# Plan for #3: Add DELETE /api/runs/:id

## Goal
Allow clients to delete existing runs through `DELETE /api/runs/:id`, returning
204 and removing the run from listings. Unknown IDs return the existing 404
shape, while runs with status `running` return 409 with `error: "run is in progress"`.
All other API behavior remains unchanged.

## Dependencies (confirmed / plausible / open), each with change: yes | no
- **confirmed — change: yes:** `src/app.ts`, `createApp`, needs a DELETE route
  and status-specific response mapping.
- **confirmed — change: yes:** `src/runs.ts`, `RunStore`, needs deletion logic
  that distinguishes missing, running, and deletable runs.
- **confirmed — change: yes:** `test/app.test.ts`, `runs api`, needs tests for
  successful deletion, unknown IDs, and running runs.
- **confirmed — change: no:** `src/config.ts` and `k8s/configmap.yaml` have no
  delete-related environment contract.
- **confirmed — change: no:** `README.md` documents the API and should add the
  new endpoint/error behavior.
- **confirmed — change: no:** `public/index.html` and `e2e/` have no existing
  run-management flow requiring this endpoint.
- **plausible — change: no:** `src/server.ts` and Kubernetes manifests are
  unaffected; verify through the normal suite and pipeline checks.

## Tests
- Update `test/app.test.ts` to verify DELETE returns 204 and the run is absent
  from GET results.
- Verify an unknown ID returns 404 with `{ error: "run not found", id }`.
- Verify a `running` run returns 409 with `{ error: "run is in progress" }`.

## Environment contract
No environment variables are added or changed. Update the README API table only;
the config code and Kubernetes ConfigMap remain unchanged.

## Risks
Deletion must be atomic with the status check so a running run cannot be
removed. Adding a way to prepare a running run for the unit test could expose
an API beyond the ticket. Pipeline risks are unit, lint, build, rollout,
stability, smoke, and browser checks.

## Open questions
1. What repository-supported setup should create a `running` run for the test:
   should `RunStore` gain a small status-transition/testable method, or should
   the store constructor accept seeded runs with explicit statuses?

## Decisions
1. Add a small `RunStore` status-transition method so the unit test can create
   a `running` run without changing constructor seed semantics.
