# Plan for #6: Add PATCH /api/runs/:id/status with allowed transitions

## Goal
Add a status endpoint that updates a run only through `planned -> running` and
`running -> done`. Unknown IDs remain 404, and invalid transitions return 409
with the current and requested statuses; all other API behavior remains intact.

## Dependencies (confirmed / plausible / open), each with change: yes | no
- **confirmed — change: yes:** `src/runs.ts`, `RunStore`, owns run status and
  needs transition validation and a result that distinguishes missing and
  invalid transitions.
- **confirmed — change: yes:** `src/app.ts`, `createApp`, needs the PATCH route,
  request validation, and HTTP error mapping.
- **confirmed — change: yes:** `test/app.test.ts`, `runs api`, needs happy-path,
  invalid-transition, and unknown-ID coverage.
- **confirmed — change: no:** `public/index.html`, `e2e/`, configuration,
  Kubernetes manifests, and README environment contract need no changes.
- **plausible — change: yes:** `README.md` API table should document the new
  endpoint and its 404/409 responses; verify against the existing API docs.

## Tests
- Test `planned -> running` and `running -> done` through PATCH requests.
- Test invalid transitions return 409 with `{ error, from, to }`.
- Test an unknown ID returns the existing 404 shape.
- Preserve existing create, list, get, and delete behavior.

## Environment contract
No environment variables are added or changed; `src/config.ts`,
`k8s/configmap.yaml`, and the README environment table remain unchanged.

## Risks
Transition checks must be atomic with the update and must not silently accept
unknown status values or skip states. Pipeline risks are the unit, build,
rollout, stability, smoke, and browser gates.

## Open questions
None.

## Decisions
Accept only a JSON body containing one of the existing `RunStatus` values and
return the updated run on success; use 400 validation errors for malformed
status input and 409 for a well-formed but disallowed transition.
