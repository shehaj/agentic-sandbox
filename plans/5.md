# Plan for #5: Enable the metrics endpoint in the deployment

## Goal
Enable the existing metrics listener in Kubernetes on a second container port
named `metrics`, and document how operators can reach it. HTTP application
behavior and the existing service port remain unchanged.

## Dependencies (confirmed / plausible / open), each with change: yes | no
- **confirmed — change: yes:** `k8s/configmap.yaml` currently disables metrics;
  set `METRICS_ENABLED=true` and provide `METRICS_PORT`.
- **confirmed — change: yes:** `k8s/deployment.yaml` currently declares only
  the HTTP container port; add the named metrics port.
- **confirmed — change: yes:** `README.md` documents the environment contract;
  add the deployed metrics endpoint and access instructions.
- **confirmed — change: no:** `src/config.ts` and `src/server.ts` already
  validate and serve the metrics listener.
- **confirmed — change: no:** `k8s/service.yaml` is not required because the
  ticket requires a container port, not a cluster service exposure.

## Tests
- Run `npm run verify`.
- Inspect the manifest diff and run the pipeline rollout and smoke checks.

## Environment contract
`METRICS_ENABLED` and `METRICS_PORT` already exist in `src/config.ts` and the
README table; the ConfigMap will provide both values.

## Risks
The metrics port must differ from the HTTP port and be named exactly `metrics`.
An invalid ConfigMap value would prevent startup and fail rollout/stability.

## Open questions
None.

## Decisions
Use container port `9100` and leave the existing `sandbox-app` Service HTTP-only,
matching the ticket's explicit container-port requirement.
