# Plan for #4: Filter runs by vehicle on the web page

## Goal
Add a labelled client-side vehicle filter above the runs table so typing filters
rows immediately and clearing the field restores all runs. API behavior and run
creation remain unchanged.

## Dependencies (confirmed / plausible / open), each with change: yes | no
- **confirmed — change: yes:** `public/index.html` renders the table and loads
  runs; add the labelled input and filtering behavior.
- **confirmed — change: yes:** `e2e/smoke.spec.ts` is the existing browser flow;
  extend it or add a focused spec for the required filter behavior.
- **confirmed — change: no:** `src/app.ts` already exposes all runs and the
  vehicle query filter; no server change is needed for client-side filtering.
- **confirmed — change: no:** `src/runs.ts`, `test/app.test.ts`, configuration,
  Kubernetes manifests, and README environment contract are unaffected.

## Tests
- Add a Playwright test in `e2e/` that types `WVW-1001` into the labelled
  filter and asserts only its two rows are visible, then clears it and checks
  all seeded rows return.
- Preserve the existing smoke checks.

## Environment contract
No environment variables are added or changed; `src/config.ts`,
`k8s/configmap.yaml`, and the README environment table remain unchanged.

## Risks
Filtering must update after the initial load and after a newly created run;
the browser test must avoid ambiguous locators. Pipeline risks are the unit,
build, rollout, stability, smoke, and browser gates.

## Open questions
None.

## Decisions
Use client-side filtering over the already-loaded run rows, matching the exact
vehicle ID as requested.
